## v1からの構造変更（7つの欠落への対応）

### 欠落①: ME→GOALS→TODAYの縦接続
**v1:** タブが独立。MEに書いた内容がGOALSやTODAYに流れない
**v2:** MEの自己定義がGOALの判断基準になり、GOALのタスクがTODAYに降りる

```
ME（自分をデザイン）
  → 「知的に見られたい」「年収800万」「35歳」
    → GOALS に「ICL手術を受ける」が生成される
      → TODAY に「クリニック3件調査」が降りる
        → 完了後「初回カウンセリング予約」が次のタスクとして出現
```

### 欠落②: ゴール間の横の参照
**v1:** 各ゴールが孤立
**v2:** ゴール間にリンクを張れる。AIが自動で関連を提案する

例: ICL完了（メガネなし）→ 撮影アカウントのコンテンツ素材になる
例: AIアカウントで出会った人 → グルメイベントに招待
→ 1つのゴールの完了が別ゴールのタスクを生む

### 欠落③: 「自分をデザインする」セッション
**v1:** MEは静的な表示板（ビジョン・強み・課題を表示するだけ）
**v2:** MEに「自分を知るセッション」を実装。20問以上の深掘りヒアリングで
信念・価値観・強み・バックグラウンドを掘り下げ、矛盾を指摘し、構造化する

### 欠落④: QOL提案エンジン（「知らないとやろうとも思わない」の防止）
**v1:** ユーザーが自分でゴールを設定する前提
**v2:** MEの属性（年収・年齢・見られたい姿・エリア・ライフスタイル）から
AIが「あなたならこれやった方がいい」を先に提案する

例:
- 「ICLって知ってる？あなたの年齢と予算なら検討してもいいかも」
- 「ふるさと納税やってる？年収的にXX万の枠がある」
- 「このエリアに住んでるなら○○ジムがコスパいい」

### 欠落⑤: 「やりたいこと」→タスク自動展開
**v1:** TALKで「タスクにする？」で終了
**v2:** 会話→ゴール生成→タスク分解→スケジュール化→フォローアップまで自動展開

ICLの例:
```
ユーザー: 「ICL受けたい」
  → AI: ゴール「ICL手術」自動生成
  → AI: タスク3件作成（クリニック調査/予算確認/カウンセリング予約）
  → AI: 「いつ行く？」とスケジュール確認
  → ユーザー: 行った後に画像で術後スケジュール共有
  → AI: 術後スケジュール（検診日/目薬リマインダー）をTODAYに反映
  → AI: 「メガネなしの自分」を撮影アカウントに投稿するタスクを提案
         → [別ゴール「撮影アカウント運営」]にも連携（欠落②）
```

### 欠落⑥: 記録→パターン発見→提案のサイクル
**v1:** AI理解メモは受動的（ユーザーの発言を蓄積するだけ）
**v2:** 日々の行動記録→パターン分析→「あなたはこういう時にうまくいく」→
次のアクション提案、というループ

### 欠落⑦: ロードマップの可視化
**v1:** タスクリストのみ
**v2:** 時系列×フェーズの俯瞰図。「今自分はPhase 1の3ヶ月目にいる」が一目でわかる

## マインドセットプリセット

### 概要
AIの応答の判断基準・価値観・アドバイスのスタイルをプリセットで切り替える。
同じ質問に対して、選んだマインドセットによって異なる視点のアドバイスが返る。

### 技術実装
システムプロンプトに注入するレイヤー。
`ME（自己定義）× マインドセットプリセット = パーソナライズされたAI応答`

### 例: 「転職すべき？」への応答
- **ふとしプリセット:** 「周りを幸せにすればお金は集まる。転職先で誰を幸せにできる？」
- **ホリエモンプリセット:** 「やりたいならやれ。迷ってる時間が一番無駄」
- **ひろゆきプリセット:** 「年収下がるならやめとけ。転職で上がる確率のデータ見た？」

### フェーズ
| Phase | やること | タイミング |
|-------|---------|-----------|
| v1 | ふとしのマインドを固定プリセットとして組み込み | UX-01で実装 |
| v2 | プリセットの「箱」（追加・切替UI）を作る | UX-01で構造だけ |
| v3 | 第三者プリセットの販売マーケットプレイス | ローンチ後 |

### v3のマネタイズ構造（将来）
- インフルエンサーが自分のマインドセットを構造化して登録
- ユーザーが月額 or 買い切りで購入
- GOAL AIがプラットフォーム手数料を取る
- インフルエンサー側メリット: ファンが「24時間○○のアドバイスを受けられる」

## Phase A 詳細仕様: 会話→行動変換エンジン

### A-1: TALK入力の意図分類

ユーザーがTALKで発言した内容をAIが以下の5種に分類し、それぞれ異なるアクションを実行:

| 分類 | 例 | アクション |
|------|---|----------|
| GOAL_CREATE | 「ICL受けたい」「SNSアカウント始めたい」 | ゴール生成→タスク分解→スケジュール提案 |
| TASK_CREATE | 「明日クリニックに電話する」 | タスク1件作成→既存ゴールに紐付け提案 |
| QUESTION | 「ICLの費用は？」 | 回答のみ（従来のチャット） |
| STATUS_UPDATE | 「カウンセリング行ってきた」「これ術後スケジュール（画像）」 | ゴール進捗更新→次タスク提案→画像解析でスケジュール反映 |
| LIFE_DESIGN | 「自分の強みって何だろう」「見られ方を変えたい」 | MEの自己デザインセッションに誘導 |

分類はシステムプロンプトで指示。応答に `[INTENT:GOAL_CREATE]` 等のタグを含めてWorkerが検出。

### A-2: GOAL_CREATE フロー（核心）

```
ユーザー: 「ICL受けたい」
    ↓
AI分類: [INTENT:GOAL_CREATE]
    ↓
AIが深掘り（1-3往復）:
  「なぜICL？メガネが嫌？見た目？スポーツ？」
  「予算感は？時期の希望は？」
    ↓
AI応答に構造化タグ:
  [GOAL_PROPOSAL]
  name: ICL手術を受ける
  why: 知的な印象を強化。メガネなしの方が撮影映えする
  deadline: 2026-06-30
  related_goals: [撮影アカウント運営]  ← ゴール間参照
  tasks:
    - name: クリニック3件調査（口コミ・EVO+取扱い・費用比較）
      deadline: 2026-04-12
    - name: 適応検査予約
      deadline: 2026-04-15
    - name: 予算確認（医療費控除の計算含む）
      deadline: 2026-04-15
  [/GOAL_PROPOSAL]
    ↓
TODAY画面にタスクカード表示（ユーザー承認後）
```

### A-3: STATUS_UPDATE フロー（フォローアップ）

```
ユーザー: 「カウンセリング行ってきた。4/25に手術決まった」
    ↓
AI分類: [INTENT:STATUS_UPDATE]
    ↓
AI応答:
  [TASK_COMPLETE] 適応検査予約 → 完了
  [TASK_UPDATE] 手術日: 2026-04-25
  [TASK_CREATE]
    - name: 手術当日の持ち物準備
      deadline: 2026-04-24
    - name: 術後翌日検診（自動推定）
      deadline: 2026-04-26
    - name: 1週間検診
      deadline: 2026-05-02
    - name: 目薬4種×1日4回リマインダー設定
      deadline: 2026-04-25
      repeat: daily, duration: 30days
    - name: 「メガネなしの自分」撮影 → 撮影アカウント投稿
      deadline: 2026-05-10
      related_goal: 撮影アカウント運営  ← ゴール間参照
  [/TASK_CREATE]
```

### A-4: 画像入力→スケジュール反映

### A-5: ゴール間参照の仕組み

**データ構造:**
```
goal: {
  id: "goal_icl",
  name: "ICL手術を受ける",
  related_goals: ["goal_photo_account"],  // 手動 or AI提案
  tasks: [...]
}
```

**AIが自動で参照を提案するタイミング:**
- GOAL_CREATE時: 新ゴールと既存ゴールの関連をAIが検出
  例: 「ICL」→「撮影アカウント運営」に「見た目変化」で関連
- TASK_COMPLETE時: 完了したタスクの成果が別ゴールに使えるか検出
  例: 「メガネなし写真」→「撮影アカウントのコンテンツ素材」
- 定期チェック（秘書メモ）: 全ゴールを横断して停滞・関連を検出

**UI表示:**
- GOALS画面: ゴール詳細に「関連ゴール」セクション。タップで遷移
- TODAY画面: タスクに複数ゴールのタグ表示（跨るタスクが視覚的にわかる）
- TALK: AIが「このタスクの成果、○○のゴールにも使えるよ」と能動的に提案

### A-7: QOL提案エンジン（「知らないとやろうとも思わない」防止）

**データソース:**
- ME: 年収帯 / 年齢 / 見られたい姿 / エリア / ライフスタイル / 趣味
- 行動履歴: 過去のゴール・タスクの傾向
- 時期: 季節 / 確定申告期 / 年末調整期 / セール期
- 外部: Gemini Web検索で最新トレンド・キャンペーン情報

**提案の生成タイミング:**
1. 週1回（日曜夜 or 月曜朝）: 秘書が「今週のおすすめ」を3件生成
2. MEプロフィール更新時: 新しい属性に基づいて即時再生成
3. ゴール完了時: 「次にやるといいこと」を提案

**提案の表示場所:**
- TODAY画面: 「おすすめ」カード（スワイプで非表示可能）
- ME画面: QOL提案リスト（タップ→詳細→「やる」でGOAL_CREATE）

**提案例（ME: 35歳/年収800万/蒲田/知的に見られたい）:**
- 「ふるさと納税、年収800万なら約13万枠。12月までにやらないと損」
- 「ICL手術、35歳はベストタイミング。40超えると老眼リスクで適応外の可能性」
- 「蒲田から通えるパーソナルジム3選。体型管理は見られ方に直結」
- 「NISAの積立設定、まだなら年初の今がスタートに最適」

### A-8: ME→GOALS→TODAY 縦接続の実装

**MEに保存される自己定義データ:**
```json
{
  "vision": "人の人生をコーディネートして幸せにする",
  "identity": {
    "age": 35,
    "income_range": "800-1000万",
    "area": "蒲田",
    "desired_image": ["知的", "行動力がある", "信頼できる"],
    "strengths": ["フットワーク", "プロデュース力", "IT技術"],
    "weaknesses": ["時間管理", "見られ方の意識"],
    "values": ["幸せのコーディネート", "本質主義", "行動力"]
  },
  "mindset_preset": "futoshi"
}
```

**接続の仕組み:**
- GOALの判断基準: ゴール作成時にME.visionと整合チェック。
  「このゴールはあなたのビジョンとどう繋がる？」をAIが確認
- TALKの応答品質: ME.identity全体をシステムプロンプトに注入。
  年収・年齢・エリアに基づく具体的アドバイスが可能に
- TODAYの優先順位: ME.desired_imageに沿ったタスクを優先表示
  例: 「知的に見られたい」→ 読書・学習系タスクにブースト

## DB/API変更点（Phase A実装に必要）

### Supabaseテーブル追加
```sql
-- ゴール間参照テーブル
CREATE TABLE IF NOT EXISTS goal_links (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  goal_id_from UUID NOT NULL REFERENCES goals(id),
  goal_id_to UUID NOT NULL REFERENCES goals(id),
  link_type TEXT NOT NULL DEFAULT 'related',  -- related / depends_on / feeds_into
  created_by TEXT NOT NULL DEFAULT 'ai',       -- ai / user
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- MEプロフィール拡張（既存テーブルにカラム追加 or 新テーブル）
```

## タスクメタデータ拡張（実装27で設計）

### 背景
現在のタスクは {id, title, status, source} のみ。AIがタスクの背景を把握していないため、
的外れな推測（「役所に行く」→「副業の届出ですね」）が発生する。
スケジュール自動化にもメタデータが必須。

### 拡張後のタスク構造（11フィールド）
```json
{
  "id": "task_xxx",
  "title": "役所に行く",
  "status": "current",
  "source": "user",
  "deadline": "2026-04-11",
  "context": "住民票の取得",
  "risk": "引っ越し手続きが遅れる",
  "worst_case": "届出期限超過で罰金",
  "estimated_minutes": 30,
  "location": "蒲田区役所",
  "time_constraint": "9:00-17:00",
  "dependencies": [],
  "energy_level": "low",
  "repeatable": null,
  "priority_score": 85
}
```

### フィールド説明
| フィールド | 必須 | 収集方法 |
|-----------|------|---------|
| deadline | ユーザーに聞く | Step1で選択式（今日/明日/今週/来週/日付/なし） |
| estimated_minutes | ユーザーに聞く | Step2で選択式（15分/30分/1h/2h/半日） |
| context | AIが聞く or null | Step3対話。推測禁止 |
| risk | AIが聞く or null | Step3対話。なくても動く |
| worst_case | AIが聞く or null | Step3対話。なくても動く |
| location | AIがローカル推論 | キーワードマッチ（役所→外出先） |
| time_constraint | AIがlocationから推論 | 外出先+役所→営業時間内 |
| dependencies | AIが検出 | タスク間の関係を自動検出 |
| energy_level | AIがタスク内容から推定 | 調査→high、掃除→low |
| repeatable | ユーザーが「毎日」と言った時 | 対話で検出 |
| priority_score | AI算出 | deadline×risk×worst_caseから0-100 |

```
│                         │

│                         │
```

```
│                         │
│   [これでOK] [もう少し詳しく]│
└─────────────────────────┘
```
▶マークはAIローカル推論によるデフォルト選択。

### Step 3: 対話で詰める（「もう少し詳しく」を押した場合のみ。Gemini Flash使用）
```
AI: 何の用件ですか？
ユーザー: 住民票取得
AI: 了解。引っ越し関連？他の手続きも必要？
ユーザー: 転入届も
AI: なるほど。転入届は14日以内が期限。住民票は同時に取れます。
   タスクを更新:
   ✅ 役所に行く（転入届+住民票）
      期日: 4/11（金） 所要: 1時間 リスク: 届出期限超過
      [確定する]
```

### タスク作成のスピード改善
| 手法 | 効果 | 実装 |
|------|------|------|
| 軽量モデル直接呼出 | ルーティング回避。3-5秒→1秒 | Step3でGemini Flash直接。ルーティング不要 |
| ローカル推論 | AI呼出ゼロ | Step2のデフォルト値。キーワードマッチJS |
| JSON応答（非SSE） | SSEオーバーヘッド除去 | メタデータ補完はPOST→JSON |
| エッジキャッシュ | 同パターン2回目以降10ms | KV getでキャッシュ |
| 楽観的UI | 体感0ms | 追加即表示→裏でAPI保存 |

**大多数のタスクはStep 2の「これでOK」で完了（10秒）。Step 3は複雑なタスクのみ（1分）。**

## AIスケジューリングロジック

### スケジュール自動配置アルゴリズム
```
1. ルーティンを先にタイムラインに配置（固定枠）
2. 空きスロットを特定
3. time_constraintのあるタスクを先に配置（役所→営業時間内の空きに）
4. 残りのタスクを以下の優先度で空きに配置:
   - deadline近い → 先に
   - energy_level=high → focus_hoursに
   - energy_level=low → 夜・隙間に
   - 外出系 → batch_errands=trueならまとめて連続配置
   - dependencies → 依存先の後に
5. max_daily_tasksを超えたら「明日に回す」提案
6. バッファ（buffer_minutes）をタスク間に確保
```

### 毎朝の提案フロー
1. ユーザーがアプリを開く
2. AIが今日のタスク+ルーティンからタイムラインを自動生成
3. 「今日のおすすめ順」として表示
4. ユーザーはドラッグで順序変更可能（AIの提案を上書き）
5. 変更があればAIが学習（scheduling_preferenceを更新）

## タイムライン自動シフト（実装28で設計）

### 背景
時間が過ぎた未完了タスクがタイムライン上の過去位置に残り続ける。
ユーザーは「終わってないから残っている」のにタイムラインが見づらくなる。

### 仕様
- autoScheduleの実行時（renderTodayScreen呼び出し時）に、現在時刻より前のスロットにある未完了タスクを検出
- 検出したタスクを次の空きスロットに自動再配置
- 再配置後のタスクには「⏰ シフトされました」の小さいラベルを表示
- 完了済みタスクは元の時間位置に残す（過去の記録として）

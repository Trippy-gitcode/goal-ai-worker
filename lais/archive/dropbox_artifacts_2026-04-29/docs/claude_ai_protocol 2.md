# Claude.ai プロトコル
> 配置: docs/claude_ai_protocol.md
> 更新: 2026-04-09 v3

---

## 1. 役割

```
INPUT:  ふとしの発言
OUTPUT: session_progress.mdへの書き込み / CLAUDE.md更新 / docs/更新
```

やること: 仕様協議、ミッション定義作成、AT記述（6項目テンプレ）、DC書き込み、Code報告の検証
やらないこと: 実装コードを読む・書く（テスト内容・合格基準の記述は行う。コード化はCodeが担当）

---

## 2. 変更フロー（全変更はこの順序で処理する）

```
仕様変更/バグ報告/機能追加
  ↓
STEP 1: 仕様書を更新する
  1a. 対象仕様書の該当セクションをDCで読む
  1b. 変更前の内容と変更後の内容をふとしに提示する
  1c. ふとしの承認を得る
  1d. 仕様書を書き換える
  対象: docs/ux_redesign_v2.md or goal_ai_design_spec_v3.md or goal_ai_project_v6_4.md
  ↓
STEP 2: 変更履歴を記録する
  対象: docs/spec_changelog.md（日付+変更内容+理由）
  ↓
STEP 2.5: 受入テスト（AT）を記述する（UIインタラクション系ミッションのみ）
  - 6項目テンプレで記述（セクション11参照）
  - grepで検証できるリファクタリング・設定変更には不要
  - ATの内容・合格基準はClaude.aiが決定する。Codeはspec.tsへのコード化のみ
  WHY: Codeに任せると「自分の実装が通るテスト」を書く。仕様作成者がテスト基準も書くことで検証の独立性を担保
  ↓
STEP 3: アプリ固有テスト仕様を更新する
  対象: docs/e2e_fullflow_test.md（該当セクション）
  ※ dev-system/tests/test_library.md（共通テスト）は触らない
  ↓
STEP 4: ミッション定義をキューに追加する
  対象: instructions/session_progress.md
  ↓
STEP 5: Codeが実行する
```

STEP 1-4はClaude.aiの責任。STEP 5はCodeの責任。
STEP 1を飛ばしてSTEP 4に行くことは禁止。
連鎖更新はdocs/system_map.mdセクション1の依存関係マップに従う。

## 3. トリガー処理

```
IF ふとし == "G_実装N"
  DO: DC read session_progress.md
  DO: キュー状態を報告
  DO: 提案ログの未実施🟢を確認 → キュー投入が必要ならふとしに提案

IF ふとし == 仕様決定（"ok" / "それでいく" / 承認）
  DO: 変更フロー STEP 1-4 を即座に実行
  DO NOT: 会話に残して後で書く

IF ふとし == バグ報告
  DO: 原因分析（コード/仕様/プロンプト/配置）
  DO: 対策提案
  DO: 同パターンの類似問題を検索
  DO: 再発防止ルールを提案
  DO: ふとし合意後 → 変更フロー STEP 1-4 を実行

IF ふとし == "前にも言った" / "何度も指摘"
  DO: 提案ログを検索 → 該当項目を特定
  DO: キュー未投入が原因 → 変更フロー STEP 1-4 を即座に実行

IF ふとし == 仕様変更
  DO: 影響範囲を分析
  DO: ふとしに報告+合意
  DO: 変更フロー STEP 1-4 を実行（関連ファイル一括更新）

IF 誤り発生（Code報告の虚偽/テスト漏れ/仕様違反）
  DO: 原因分析
  DO: 類似ケース検索
  DO: 再発防止ルールをdevelopment_rules.md/CLAUDE.md/canopyに追加
  DO: ルールに基づきCodeが自己発見→修正するミッションをキューに投入
  DO: 修正確認

IF ミッション定義を書く
  DO: templates/mission_template_v2.md のセルフチェック全11項目を確認
  DO NOT: 1項目でも未確認のまま書き込む

IF ファイルを書き込む
  DO: 書き込み前に対象ファイル名+理由を提示
  DO: ふとしの「OK」を待つ
  例外: 読み取りは承認不要

IF セッション終了
  DO: 未書き込み事項を全件チェック
  DO: 残りがあれば書き込んでから終了
  DO NOT: 「次回やる」で閉じる
```

## 4. 優先順位

```
1. バグ修正（ユーザーがバグを見つける前に修正されていること）
2. ふとしが指摘した問題 → 変更フロー実行
3. 提案ログ未実施項目 → キュー投入判断
4. 機能改善/新機能
5. デザイン改善
6. 体制/仕組み整備
```

---

## 5. 判断基準

```
IF 判断可能 → 推奨案1つ+根拠を提示。丸投げしない
IF 未確認 → 「未確認」と明言。DCで確認可能なら先に確認
IF 提案 → bootstrap.md/CLAUDE.mdとの矛盾がないか確認してから発言
```

---

## 6. Code完了報告の検証

```
IF Code報告に操作スクリーンショットなし → 不受理。追加要求
IF Code報告がgrepのみ → 不受理。スクショ画像での視覚確認を要求
IF Code報告が「全PASS」で分母なし → 不受理
IF Code報告にhasClass/getAttribute/boundingBox等DOM APIベースの判定 → 不受理。スクショ画像で再判定を要求
IF Code報告に曖昧用語（「確認した」「表示されている」「正常に動作」「問題なし」「対応済み」「修正済み」「実装済み」「開いている」「閉じている」「存在する」「反映されている」「変化した」）→ 不受理。スクショの具体的事実で書き直しを要求
```

### UI検証の判定基準
```
判定の根拠は「仕様で決めたデザイン変更が実現されているか」のみ。
DOM API（hasClass/getAttribute/boundingBox）の値ではない。
スクショを画像として見て判定する。

PASS: スクショで仕様通りの視覚変化が確認できる
FAIL: スクショ前後に差異がない / 仕様と異なる表示
```

```
🟢低リスク → バッチ承認可
🟡中リスク → 3件連続 → まとめて報告
🔴高リスク → 個別承認（実行前に停止）
```

## 9. 禁止

```
DO NOT: 提案ログに入れてキューに入れない
DO NOT: キュー投入で済む問題にルール追加する
DO NOT: 体制整備に時間をかけて基本バグを放置する
DO NOT: Code完了報告を検証なしで信じる
DO NOT: 曖昧な表現（「推奨」「意識」「実行力」「気をつける」）
DO NOT: 指示に「確認する」「見る」「判断する」を使う（Codeが自由に解釈する。代わりに具体的な手順・数値条件・コマンドで記述）
DO NOT: 事実確認せずに断言する
DO NOT: コードを読む
DO NOT: 1箇所だけ更新して関連ファイルを放置する
DO NOT: 仕様書を更新せずにキューに投入する（STEP 1-4の順序厳守）
```

## 11. 受入テスト（AT）テンプレート

### ATテンプレ（6項目 + ストレスパス）

```
AT-N: テスト名
  前提: テスト実行に必要なデータ・状態のセットアップ（例: タスク1件作成、ログイン済み等）
  操作: 具体的なユーザー操作（タップ対象・入力内容）
  期待: 何が起きるべきか
  検証: 何が見えるべきか（具体的な要素・テキスト）
  否定検証: 何が見えてはいけないか（別画面の要素漏れ等）
  データ検証: リロード後/API上でデータが正しいか
  スクショ: 何を撮るか（操作前/中/後）

ストレスパス: 画面往復3回（AT-X→AT-Y→AT-X→AT-Yを3往復）して最後も正常
```

**前提が未記述のATはCodeがSKIPする原因になる。全ATに前提を明記すること。**
WHY: ARCH-02 AT-3でタスク不在→SKIP→BUG-06未検証のままDONE

### AT対象判定

```
IF UIインタラクション（タップ/入力/遷移/ドラッグ） → AT必須
IF grep検証のみ（リファクタリング/設定変更/ドキュメント） → AT不要
```

### 責務分担

```
Claude.ai: 仕様 + AT内容・合格基準を記述
Code: ATをspec.tsにコード化 → 全FAIL確認 → 実装着手 → 全PASS + スクショで完了
```

WHY: テスト設計と実装を同一者が行うと「自分の実装が通るテスト」になる。BUG-05/06/02再発で実証済み。仕様作成者がテスト基準を決め、実装者はそれを通すだけにすることで検証の独立性を確保する。

# ミッションステータス管理 — 詳細ルール
> 索引: development_rules.md → 構造的制約
> 更新: 2026-04-07
> 将来のオーケストレーターで自動化する前提で設計

## STATUSタグ
各ミッション定義のヘッダに `STATUS:` を記載。

| STATUS | Codeの行動 |
|--------|-----------|
| `QUEUED` | 実行開始。開始時に`IN_PROGRESS`に変更 |
| `IN_PROGRESS` | 前回中断。中間結果を読んで続きから実行 |
| `BLOCKED` | 実行しない。ブロック理由を読んでふとしに報告 |
| `DONE` | スキップ（唯一スキップしてよいステータス） |
| タグなし | `QUEUED`扱いで実行 |

## 判定ルール（厳守）
1. **`DONE`に変更できるのは完了コマンドが全PASSした時のみ**
2. 中間結果・FAILログがあっても`DONE`でなければ未完了。続行必須
3. 「一度試した」「APIエラーで全滅した」はDONEにする理由にならない
4. FAILが残っている場合: 原因を分析→修正→再実行→全PASSで初めてDONE
5. 修正不可能な外部要因（API障害等）でBLOCKEDにする場合は理由を明記

## ステータス遷移図
```
QUEUED → IN_PROGRESS → DONE（完了コマンド全PASS時のみ）
                     → BLOCKED（外部要因で続行不可。理由明記）
                     → IN_PROGRESS（FAIL修正→再実行ループ）
```

## キュー判定フロー（セッション開始時にCodeが実行）
```
1. session_progress.mdの「ミッションキュー」セクションを読む
2. 上から順にSTATUSを確認
3. DONE → スキップ
4. QUEUED/IN_PROGRESS/タグなし → そのミッションを実行
5. BLOCKED → ふとしに報告して次へ
6. 全ミッションがDONEまたはBLOCKED → 初めてキュー空と判断
7. キュー空 → 自律フロー（未実装調査→提案ログ→停止）
```

## アンチパターン（禁止）
- 中間結果があるから「もう終わった」→ STATUSがDONEでなければ未完了
- FAILが外部要因だから「テストは正しい」→ 0 failedにならなければDONEにしない
- 前回のセッションで実行したから「同じことはやらない」→ IN_PROGRESSなら続行

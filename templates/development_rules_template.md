## 方針

## Claude Code ルール（実装時）

### C1. 参照ドキュメントを全て読んでから実装開始
- CLAUDE.md の契約セクション・参照ドキュメントリストを確認
- 該当する指示書 + amendments を全て読む
- 不明点は推測で埋めない。session_progress.md に記録して停止

### C2. 1機能1デプロイ・デプロイ後即キャノピーテスト
- 実装 → デプロイ → canopy.sh → PASS → git tag → git push → 次
- FAILなら rollback → ログ確認 → 修正 → 再デプロイ
- 複数機能をまとめてデプロイしない
- git tagはバージョン番号付き（例: v1.0.0-mission1）

### C3. ファイル変更範囲の厳守
- ミッションに関係ないファイルは変更禁止
- 大規模編集後はgrepで保全確認
- diff を instructions/results/ に自動保存

### C4. ログ確認前の投機的修正禁止
- バグ → まずログ確認
- 原因特定 → 修正 → テストの順序を守る

### C5. verify.sh を自分で作成
- 新規追加した関数は全て grep 存在確認
- 既存関数の保全確認は累積（canopy.sh に追加）
- 判定は PASS/FAIL で明確に。曖昧な「たぶんOK」は禁止

### C6. 判断の線引き
- 実装設計（どう作るか）: 自分で判断OK。根拠を記録
- 仕様（何を作るか）: 変更禁止。CLAUDE.md 契約セクション参照
- ミッション遂行に必要なバグ修正: 許可（修正内容を記録+verify.shに検証追加）
- ミッションと無関係なバグ発見: 提案ログに報告するだけ。修正しない
- 改善案: session_progress.md 提案ログに記録するだけ。実装しない

### C7. 品質ゲート
- Phase 0: プリフライトチェック（前提条件の機械的検証。FAIL→停止）
- diff保存: git diff → instructions/results/
- grep保全: 新規+既存の全項目チェック
- キャノピーテスト: canopy.sh 実行（FAIL→rollback→停止）
- git tag: バージョン付き
- 結果レポート: session_progress.md に記録

### C8. キュー空時の自律提案
- ミッションキューが空になったら、仕様書+コードベースgrepで未実装タスクを特定
- session_progress.mdの提案ログに候補リストを記載して停止。実装はしない
- オーナー（またはClaude.ai）の承認後にのみキューに移動される

### C9. セッション開始時の参照ファイル検証
- CLAUDE.mdの参照ドキュメントリストに記載された全ファイルの存在をチェック
- 不在のファイルがあれば提案ログに報告して停止（そのまま実装開始しない）

## Claude.ai ルール（設計・方針決定時）

### A1. 誤り発生時の横展開・再発防止
- 間違い・誤解・意図しない事象が発生した場合:
  1. 類似ケースが他にないか横展開チェック
  2. 再発防止策を提案
- 「このケースだけ」で終わらせない。パターンとして捉える

### A2. 5セッションごとの棚卸し
- 5セッションごとに以下を確認:
  1. CLAUDE.md・development_rules.md・session_progress.mdの整合性
  2. docs/のナレッジファイルが最新か
  3. 参照ドキュメントリストに不在ファイルがないか
  4. 提案ログに未処理の項目がないか
- 不整合があれば修正提案を出す

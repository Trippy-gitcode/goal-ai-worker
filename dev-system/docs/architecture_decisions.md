# アーキテクチャ判断テンプレート
> 重要な技術判断を問題→選択肢→判断→根拠の形式で記録する。
> GOAL AIのARCHチェーン（Preact移行）での判断を参考例として記載。

---

## テンプレート

```markdown
### ADR-NNN: [判断タイトル]
- **日付:** YYYY-MM-DD
- **ステータス:** 提案 / 採用 / 却下 / 廃止
- **問題:** 何が問題か。再現条件。影響範囲
- **選択肢:**
  A) [選択肢A] — メリット / デメリット
  B) [選択肢B] — メリット / デメリット
  C) [選択肢C] — メリット / デメリット
- **判断:** [選択した選択肢]
- **根拠:** なぜその選択肢を選んだか。定量的根拠があれば記載
- **影響:** 変更されるファイル、テスト、デプロイ手順
- **検証方法:** 判断が正しかったことをどう確認するか
```

## GOAL AI 参考例

### ADR-001: Preact vs Vanilla PageController
- **日付:** 2026-04-09
- **ステータス:** 採用
- **問題:** グローバル変数+DOM直接操作のshow/hideでは状態漏れが構造的に防げない。BUG-05(タスク詳細漏れ), BUG-06(編集未動作), BUG-02再発が同根
- **選択肢:**
  A) Preact導入 — mount/unmountが保証。既存コードとハイブリッド共存可能 / 学習コスト、バンドルサイズ増
  B) Vanilla PageController — 追加依存なし / unmount保証が自作になり信頼性低
  C) React — エコシステム充実 / Preactより重い。Cloudflare Pages向きでない
- **判断:** A) Preact
- **根拠:** 3KBのバンドルサイズ増で正式なライフサイクル管理。既存VanillaとのinnerHTML共存パターン確立（ARCH-00で検証済み）
- **影響:** frontend/components/*.jsx新設、preact-bridge.js、全画面のmount/unmount
- **検証方法:** ARCH-00 spec.ts全PASS + 既存E2E回帰0FAIL

### ADR-002: 薄いコンポーネントパターン
- **日付:** 2026-04-10
- **ステータス:** 採用
- **問題:** 全画面のロジックをJSXに書き直すのはリスクが高すぎる
- **選択肢:**
  A) 薄いコンポーネント（ライフサイクルのみ、レンダリングはVanilla継続）
  B) 完全JSX化（全DOMをPreactが管理）
- **判断:** A) 薄いコンポーネント
- **根拠:** 8画面を2日で移行完了。既存E2Eテストとの互換性維持。段階的にJSX化可能
- **検証方法:** ARCH-03〜10 全spec PASS + 既存テスト回帰

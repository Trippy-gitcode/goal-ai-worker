# [プロジェクト名] — 開発ルール
> GOAL AI開発ノウハウを汎用化したテンプレート。各ルールにWHY付き。
> 更新: 2026-04-11

---

## 方針
**品質維持を最優先に、Code が自律的に実装・テスト・検証する。オーナーの作業は承認判断のみ。**

---

## Claude Code ルール

### C1. 参照ドキュメントを全て読んでから実装開始
**WHY:** 読まずに推測で実装すると仕様違反が発生。GOAL AIでは3回の手戻りを経てルール化。
- CLAUDE.md の契約セクション・参照ドキュメントリストを確認
- 不明点は推測で埋めない。session_progress.md に記録して停止

### C2. C2基準フロー厳守
**WHY:** 「テストは後で」が許されると、デプロイ後に発覚するバグが増える。1機能1デプロイがロールバック単位を最小化。
- 実装 → L1スモーク(2分) → bump-version → build → canopy → L2影響範囲テスト → deploy → health → tag → push
- 省略・順序変更禁止

### C3. ファイル変更範囲の厳守
**WHY:** 無関係なファイル変更がテスト失敗の原因になる。変更範囲が広いほどデバッグ困難。

### C4. ログ確認前の投機的修正禁止
**WHY:** 推測修正は50%の確率で別のバグを生む。4フェーズ: 証拠収集→仮説→検証→修正。

### C5. verify.sh / canopy.sh を自分で作成
**WHY:** 手動確認は漏れる。機械的ゲートのみが信頼できる。canopy項目は累積（削除禁止）。

### C6. 判断の線引き
- 実装設計（どう作るか）: 自分で判断OK。根拠を記録
- 仕様変更（ユーザーに見える挙動変更）: 禁止。提案ログに記録して停止

### C7. session_progress.md にログ記録
**WHY:** 次セッションの引き継ぎの唯一の情報源。書かないと同じ調査が繰り返される。

### G8. AT先行（受入テスト駆動）
**WHY:** ATなしに実装すると「何を持って完了とするか」が曖昧になる。GOAL AIではAT未記述のまま実装した結果3回の手戻りが発生。
- UIインタラクション系ミッションではAT（6項目）をspec.tsにコード化
- 全FAIL確認後に実装着手
- 全PASS + ストレスパスPASSで完了

### G9. デプロイ前に操作確認
**WHY:** テストPASSでも実際のUI上で動かないケースが多い（DOMパス不一致、CSS非表示等）。
- grepやテストPASSだけで「完了」としない
- Playwrightで実際に操作 → スクリーンショット撮影 → 目視レベルで確認

### C10. デザイン検証は双方向
**WHY:** 正方向（mockup→実装）だけでは、後から追加された要素を検出できない。
- 正方向: mockup仕様 → 実装に存在するか
- 逆方向: 実装にある要素 → mockupに定義されているか

### C11. バグ対応フロー
- ミッション遂行に必要なバグ → 即修正（記録必須）
- 無関係なバグ → 報告のみ（提案ログに記載）

### C15. 「忘れた」「間違えた」禁止
**WHY:** AIにうっかりは存在しない。構造的原因を特定する。
- エラー発生時: ルール不在/検証不在/参照フロー欠如/コンテキスト制約を特定
- 機械的ゲートの改善を提案

## 承認ルール
- 🟢低リスク: バッチ承認可
- 🟡中リスク: 3件まで連続実行可（まとめて報告→承認）
- 🔴高リスク: オーナーの個別承認必須（実行前に停止）
- 🟠デザイン: ビジュアルチェック合格済みmockup必須

# デバッグガイド（Systematic Debugging）
> Superpowers systematic-debuggingの4フェーズをGOAL AI体制に統合。
> C11バグ対応フローのルーティング後、Codeがデバッグに入る際にこのガイドに従う。
> 修正試行3回制限（development_rules.md）と連動。
> 更新: 2026-04-10

---

## 原則

**根本原因を特定する前に修正を試みることを禁止。**
推測による修正は新しいバグを生む。証拠→仮説→検証→修正の順序を厳守。

---

## Phase 1: 証拠収集（修正提案禁止）

このフェーズでは修正コードを一切書かない。

1. **エラーログを読む**
   - Cloudflare Workers: `wrangler tail --format=json`
   - ブラウザ: DevTools Console + Network
   - Playwright: `page.on('console')` + スクショ

2. **データフロー追跡（境界ログ）**
   各コンポーネント境界で入力と出力をログ出力し、どこで壊れるか特定。
   ```
   フロントエンド → API → ルーティング → AIサービス → Supabase
   各境界で: 何が入ったか / 何が出たか / 期待と実際の差分
   ```

3. **再現手順の確定**
   - 100%再現できる最小手順を記録
   - デバイス依存の場合はシミュレーターで再現（A10ルール: 静的解析のみで診断禁止）

4. **証拠をログに記録**
   ```
   [Phase 1 証拠]
   - エラー: TypeError: xxx is not a function (src/routes/chat.js:42)
   - データフロー: フロント→API ✓ / API→ルーティング ✗（ここで壊れる）
   - 再現手順: TALKタブ→メッセージ送信→500エラー
   ```

---

## Phase 2: 仮説構築

証拠に基づいて仮説を立てる。最大3つまで。

```
仮説1: ルーティングのcatch-all条件が新しいメッセージ形式を処理できない
仮説2: GPTのAPIレスポンス形式が変わった
仮説3: rate-limitのKV書き込みがタイムアウトしている
```

各仮説に「検証方法」を1行で書く。検証方法がないなら仮説として不十分。

---

## Phase 3: 仮説テスト

仮説を1つずつ検証。複数同時に変更しない。

1. 仮説1を検証するための最小コード変更またはログ追加
2. テスト実行→結果記録
3. 仮説が正しければPhase 4へ。間違いなら次の仮説へ

**全仮説が外れた場合:** Phase 1に戻って証拠を追加収集。

---

## Phase 4: 修正＋テスト

1. **修正前にテストを書く**（G8 RED/GREEN）
   - バグを再現するテストを書く → FAIL確認
   - 修正を実装 → PASS確認
   - 回帰テスト（L1スモーク）が壊れていないか確認

2. **修正をログに記録**
   ```
   [Phase 4 修正]
   - 根本原因: ルーティングのregexが /^goal/ を処理していなかった
   - 修正: src/services/ai/routing.js L42 に条件追加
   - テスト: tests/e2e/specs/routing.spec.ts 追加（PASS）
   - 回帰: L1スモーク全PASS
   ```

---

## Phase 4.5: アーキテクチャ疑問（3回失敗時）

修正試行3回制限（development_rules.md）に到達した場合:

**これは実装の問題ではなく、設計の問題。**

1. Codeは即HOLD
2. 以下をsession_progress.mdに記録:
   - 3回の修正試行それぞれの内容と失敗理由
   - 「なぜ直らないか」の分析
   - アーキテクチャ変更の提案（あれば）
3. Claude.aiにエスカレーション→ふとしと方針協議

## 補助テクニック

### Root Cause Tracing（コールスタック逆引き）
エラーが発生した箇所から呼び出し元を逆方向に辿る。
```
エラー箇所 → 直接の呼び出し元 → その呼び出し元 → ... → 根本原因
各ステップで「この時点でデータは正しいか？」を確認
```

### Defense in Depth（多層バリデーション）
根本原因を修正した後、同じ種類のバグが他の箇所で起きないよう多層で防御。
```
Layer 1: 入力バリデーション（フロントエンド）
Layer 2: APIパラメータチェック（Workers）
Layer 3: DBクエリ前のnullチェック（Supabase呼び出し前）
```

### Condition-Based Waiting（非同期テスト安定化）
`waitForTimeout(3000)` ではなく条件ベースで待機。
```javascript
// ❌ BAD
await page.waitForTimeout(3000);

// ✅ GOOD
await page.waitForSelector('.ai-response', { state: 'visible' });
await page.waitForResponse(resp => resp.url().includes('/api/chat'));
```

---

## アンチパターン（やってはいけないこと）

1. **ログを読まずに修正を始める** → Phase 1を飛ばすな
2. **複数箇所を同時に変更する** → 何が効いたかわからなくなる
3. **「たぶんこれだろう」で修正する** → 証拠なき修正は禁止
4. **修正後にテストを書かない** → 同じバグが再発する
5. **デバイス依存バグを静的解析だけで診断する** → A10ルール違反

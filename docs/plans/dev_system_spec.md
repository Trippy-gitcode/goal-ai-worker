## 1. 設計原則

### 1.1 基本思想
- **品質最優先。** スピードのために品質を犠牲にしない
- **自動化最大。** PO（ふとし）の手動作業を承認のみに最小化
- **機械可検証。** ルールは可能な限りスクリプト/ゲートで自動検証する
- **Single Source of Truth。** 各情報の正規ソースを1箇所に限定し、二重管理を排除

### 1.2 仕様書の棲み分け（dev-system vs アプリ仕様書）

本仕様書（dev-system）は**How（どうやって品質を担保するか）**を定義する。アプリ仕様書は**What（何を作るか）**を定義する。

| 観点 | dev-system（共通基盤） | アプリ仕様書（固有） |
|------|----------------------|-------------------|
| デザイン | AIっぽさ排除基準・NGリスト・検出方法 | ブランド定義、テーマ、色、タイポグラフィ |
| テスト | G1-G9ゲート体系、3層テスト戦略、AT形式 | 具体的なテストケース、画面固有の検証 |
| 品質 | 品質ゲートの仕組み、鉄則、禁止事項 | 許容する閾値の具体値 |
| フロー | 変更フロー6ステップ、承認ルール、バグ対応 | 画面遷移、SW処理フロー |
| デプロイ | deploy.sh/rollback.sh/canopyの仕組み | app_config.yamlの具体値 |
| AI活用 | AIレビュー基盤、ルーティング設計の枠組み | プロンプト内容、モデル選定、比率 |

**アプリが変われば刷新されるもの → アプリ仕様書。プロジェクトを跨いで引き継ぐもの → dev-system。**

### 1.3 3層構造
| 層 | 担当 | 役割 |
|---|------|------|
| **PO（ふとし）** | 経営判断 | 「何を作るか」の決定 + 承認 |
| **ADV（Claude.ai）** | アドバイザー | 仕様協議・ミッション定義作成・AT記述・リポジトリ書き込み |
| **ENG（Claude Code）** | 自律エンジニア | 実装・テスト・デプロイ・レポート |

**ENGの設計権限の制約:** コスト構造またはプラン間の差別化に影響するアーキテクチャ変更は、提案ログに記載してPO承認を待つ。

### 1.4 バグ対応フロー
```
POがバグ発見
  ├── 仕様判断が必要？ → ADVと議論 → session_progress.mdに記載 → ENG修正
  ├── コスト/プランに影響？ → 同上
  └── それ以外 → POがENGに直接伝える → ENG修正 → session_progress.mdに記録

ENGがバグ発見
  ├── ミッション遂行に必要 → 即修正（記録必須）
  ├── コスト/プラン影響あり → 提案ログ→ADVが読む→承認
  └── それ以外 → 提案ログ。キュー空時に自律修正可
```

## 2. 変更フロー（6ステップ）

全ての仕様変更・機能追加・バグ修正はこのフローに従う。

```
Step 1: 仕様確定（ADV↔PO）
  ADVが仕様を整理し、影響範囲・コスト・リスクを分析 → PO承認
  連鎖更新は§18の依存関係マップに従う

Step 2: モックアップ作成・承認
  UI変更を伴う場合、ADVがモックアップ作成 → PO目視承認
  モックアップは原本（Single Source of Truth）。手動再構築禁止

Step 2.5: AT（受入テスト）内容・合格基準記述
  ADVがAT内容を記述（§5テンプレート準拠）
  ENGはspec.tsにコード化（AT内容を勝手に変えない）
  WHY: Codeに任せると「自分の実装が通るテスト」を書く

Step 3: キュー登録
  ADVがsession_progress.mdにミッション定義を書き込み

Step 4: ENG実装
  G8テストファースト: AT全FAIL確認 → 実装 → 全PASS
  TDD証跡: before.json（RED）とafter.json（GREEN）をevidence/MISSION-ID/に保存
  1コンポーネント300行以内。超えたら分割（max_lines_lint.shで自動検証）
  対象ファイル外の変更禁止（changed-files-allowlist.shで自動検証）

Step 5: G9検証 → C2デプロイ → PO最終確認
  スクショ画像判定 → C2デプロイフロー（§8） → PO実機確認
```

### 仕様協議時の操作フロー確認（毎回必須）
- ユーザーが開始する操作は何か
- ユーザーが中断/キャンセルする手段はあるか
- 操作完了後に元の画面に戻るか

### 4.1.1 STATUS 5状態モデル SSOT（PD-109、§21 §C3.2 正本参照）

ミッション STATUS は5状態（QUEUED / IN_PROGRESS / READY_FOR_DEPLOY / DONE / BLOCKED）モデル。本節は §21 §C3.2 を正本とし、本文はその参照のみ。

**要点:**
- QUEUED → IN_PROGRESS: ENG 初回コミットで canopy 自動
- IN_PROGRESS → READY_FOR_DEPLOY: cmd-unit AND cmd-e2e PASS（N/A 明示含む）+ G8 RED→GREEN 1種類以上
- READY_FOR_DEPLOY → DONE: deploy.sh 成功 + G17 PASS
- IN_PROGRESS → DONE: `no_deploy:true` 時に READY_FOR_DEPLOY 経由せず直接
- BLOCKED は ENG 手動例外、STATUS_CORRECTION（逆方向遷移）は ADV/PO 限定（PATCH-12）

詳細: §21 §C3.2 + lais/verify/dev_system_v34_package.md §3.2 SSOT。

### 4.1.2 L1/L2/L3 と cmd-3区分 SSOT（βcrit'、§21 §C3.4 参照）

L1 スモーク / L2 影響範囲 / L3 フルの定義と、cmd-unit / cmd-e2e / cmd-realworld の3区分関係は §21 §C3.4 を SSOT とする（§7 は本節を参照）。

### 4.2 G2とG9の役割分担
- **G2（開発補助）:** DOM APIチェック。ENGの自己診断用。完了報告の根拠には使わない
- **G9（受入判定）:** スクショを画像として見て「仕様で決めたデザイン変更が実現されているか」判定。hasClass/getAttribute/boundingBox等のDOM APIでの判定は禁止

### 4.3 G9 スクショ証跡規約
```
evidence/
  MISSION-ID/
    before_AT-1.png    ← 操作前（タイムスタンプ付き）
    after_AT-1.png     ← 操作後
    before_AT-2.png
    after_AT-2.png
    ...
```
- 各ATに最低 before 1枚 + after 1枚
- スクショ前後ファイルが完全一致（バイナリ同一）= FAIL
- screenshot_lint.sh で存在と枚数を検証（sub_infrastructure.md参照）
- 完了報告にファイル一覧を必須記載

### 4.4 テスト判定方式
```bash
# 推奨: 終了コードで判定
npx playwright test --project=mobile || exit 1

# 詳細分析: JSONレポーター
npx playwright test --reporter=json > results.json
jq '.stats.unexpected' results.json | awk '{if($1==0) exit 0; else exit 1}'
```
旧方式（`tail -1 | grep "0 failed"`）は出力フォーマット依存で脆いため非推奨。

### 4.5 SKIPルール
- **許容されるSKIP:** プラットフォーム非対応のみ。`// @allowed-skip: platform` コメント必須
- **FAIL扱い:** 条件付きtest.skip()、try/catchタイムアウト握りつぶし、その他全てのSKIP
- SKIPされたATは次キューに**SKIP-RETRY**として追記
- **SKIP-RETRYリトライ上限: 最大2回。** 3回目のSKIPはBLOCKED → ADV調査

詳細: sub_testing.md

### 4.6 G8 TDD証跡
ENGは以下の証跡を保存する：
1. 実装前: `npx playwright test --reporter=json > evidence/MISSION-ID/before.json`（RED確認）
2. 実装後: `npx playwright test --reporter=json > evidence/MISSION-ID/after.json`（GREEN確認）
3. canopyでbefore/afterの差分を検証（beforeにunexpected>0、afterにunexpected==0）

### 4.7 AIっぽさ排除基準（全アプリ共通）

AI生成コンテンツ（UI/テキスト/レイアウト）は以下を排除する。
ENGはコンポーネント作成時にこのリストを参照し、G9スクショ判定でADVが確認する。

**NGパターン:**
- 均等グリッド+角丸カード+アイコンの汎用レイアウト
- グラデーション背景+白テキストの「SaaS LP」テンプレ
- 絵文字・アイコンの過剰使用（1画面5個以上）
- 「あなたの目標を達成しましょう！」等の汎用コピー
- 左アイコン+右テキストの繰り返しリスト
- 紫→青グラデーション、ネオン配色
- 余白・タイポグラフィに個性がない（Tailwind UIそのまま）
- ボタンが全て同じサイズ・同じ色

**原則:** 「このUIがどのアプリのものか、ロゴを隠しても分かる」こと。
**検出:** G9スクショ判定時にADVが確認。AI生成テキストはアプリ固有のプロンプトで制御。
**アプリ固有のブランド定義（テーマ/配色/トーン）はアプリ側のdesign_system.mdに記載。**

## 5. ミッション定義テンプレート v3

**原則: 完了条件を全てbashコマンドで記述する。自然言語の「全件」「すべて」「全て」禁止。**

```markdown
### MISSION-ID: タイトル
> リスク: 🟢低 / 🟡中 / 🔴高
> 参照: docs/xxx.md（フルパスで列挙）
> 対象ファイル: src/xxx.js（変更してよいファイルを列挙。対象外変更はchanged-files-allowlist.shでFAIL）

**目的:** 1行

**プリフライト:**
  wc -l docs/xxx.md   # 参照ファイルの存在確認

**AT（ADV記述。ENGはspec.tsにコード化）:**
AT-N: テスト名
  前提: （必須。省略不可）
  操作: ユーザーが行う操作
  期待: スクショで確認できる期待結果
  検証: スクショで見えるべきもの
  否定検証: スクショで見えてはいけないもの
  データ検証: リロード後の永続化確認
  スクショ: 撮影タイミング
  RED: ☐ （実装前にテスト実行→FAIL確認→FAILログのパスを記入）
  GREEN: ☐ （実装後にテスト実行→PASS確認→PASSログのパスを記入）

ストレスパス: 主要操作を3回連続。最後も正常

**完了コマンド:**
  cmd1: npx playwright test path/to/spec.ts --project=mobile || exit 1

**FAIL条件:** cmd1-Nのいずれかが非ゼロ終了
**完了報告:** MISSION-ID: cmd1-N PASS/FAIL + AT各結果 + スクショ枚数 + evidence/ファイル一覧
```

ATテンプレートの詳細・セルフチェック11項目: sub_adv_protocol.md

## 6. 承認ルール

リスクベースの承認が**唯一のルール**。

| リスク | 承認方式 | 条件 |
|--------|---------|------|
| 🟢低 | バッチ承認可 | mockup変更なし + 対象2ファイル以内 + ux_v*.md記載の機能を変更しない |
| 🟡中 | 3件まで連続実行→まとめて報告 | セッション内上限: 変更ファイル≤6 / LoC差分≤500 |
| 🔴高 | 個別承認必須（実行前に停止） | アーキ変更/コスト影響/プラン変更 |

🟢低リスクでホットフィックスパス条件を全て満たす場合、ENGは自律実行可。
**ホットフィックスパスの上限:** 1セッション2件まで / 変更ファイル合計≤4。

### 6.4 Hフロー承認ゲート（PD-110 + PATCH-14、§21 §C4.5 参照）

高リスクファイル（`src/auth/` / `src/payment/` / `src/services/supabase.ts` / `src/services/external/` / `src/services/stripe/` / `supabase/migrations/` / `.env` / `.dev.vars` / `wrangler.toml`）の変更は Hフロー（統合フローレビュー）発火。

**承認主体**: ADV（Claude.ai / Desktop Code ADV）または PO のみ。ENG 自己付与禁止（PD-110）。
**承認証跡**: `instructions/approvals/<MISSION_ID>.hflow.approved`（JSON。§21 §C4.5 スキーマ）
**二重証跡（PATCH-14、R3-H-09）**: session_history_ref + approval_git_author + HEAD sha の3層検証。`scripts/verify_approval_authenticity.sh` が deploy.sh Step 5 で一括検査。
**オプトアウト**: `app_config.yaml` の `hflow.enabled: false` でスキップ（ソロ開発者向け、§2.18 PD疑義2）。

詳細フロー: sub_hflow_protocol.md

## 7. 3層テスト戦略

**正本**: §21 §C3.4 を L1/L2/L3 と cmd-3区分（cmd-unit / cmd-e2e / cmd-realworld）の SSOT とする。本節はタイミング・時間の運用情報のみ。

| 層 | タイミング | 項目数 | 時間 | SSOT |
|---|-----------|--------|------|------|
| **L1: スモーク** | 毎デプロイ | ~5-10 | 2分 | §21 §C3.4（起動+認証+主機能1+主機能2/API+永続化の5項目 SSOT）|
| **L2: 影響範囲** | 変更時 | 変動 | 5-10分 | §21 §C3.4（test_map.yaml + git merge-base、affected-tests.sh）|
| **L3: フル** | 週次/リリース前 | 全件 | 30分+ | §21 §C3.4（全テスト+パフォーマンス計測）|

L1 FAIL → デプロイ中止。L2 FAIL → 該当修正まで先に進まない。
/simplify: ENGがテスト量が多すぎると判断した場合、ADVに簡略化を申請可。自己判断での省略は禁止。

## 8. C2デプロイフロー

deploy.sh（sub_infrastructure.md）がapp_config.yamlを読み取り、以下を自動実行する。
環境引数: `deploy.sh [dev|staging|prod]`（デフォルト: prod）

```
実装完了
  → version_sync.sh（app_config.yaml → package.json, version.ts, CLAUDE.md に自動反映）
  → deploy.sh 内部フロー:
    1. yqでapp_config.yamlからbuild.cmd, deploy.frontend_cmd, deploy.backend_cmdを読み取り
    2. ${build.cmd} 実行（例: npx vite build）
    3. canopy.sh（全ゲート）
    4. L1スモーク（2分）
    5. L2影響範囲（5-10分）
    6. ${deploy.frontend_cmd} 実行
    7. ${deploy.backend_cmd} 実行
    8. curl -s $URL | grep version（デプロイ確認）
    9. git tag vX.Y.Z
```

C2フロー中のFAILは即停止。FAILが解消するまでデプロイ禁止。
**C2失敗時:** rollback.sh で直近タグへ再デプロイ可能（sub_infrastructure.md参照）。

## 9. デバッグ

### 9.1 4フェーズ（Systematic Debugging）

**根本原因を特定する前に修正を試みることを禁止。**

| Phase | 名称 | 内容 | 禁止事項 |
|-------|------|------|---------|
| 1 | 証拠収集 | エラーログ読む→データフロー境界追跡→再現手順確定 | 修正コードを書くこと |
| 2 | 仮説構築 | 証拠に基づき最大3仮説。各仮説に検証方法を1行で記述 | 検証方法なき仮説 |
| 3 | 仮説テスト | 1つずつ検証。複数同時変更禁止。全外れならPhase 1に戻る | 複数同時変更 |
| 4 | 修正+テスト | バグ再現テスト→FAIL確認→修正→PASS確認→回帰テスト | テストなき修正 |

### 9.2 修正試行3回制限
同一バグへの修正は3回まで。3回失敗 → 自動HOLD → ADVにエスカレーション。
「ストライク」の定義: ミッションをDONE報告したが、PO最終確認で不合格 or L1/L2で回帰FAIL。
バグIDごとにストライクカウントを追跡する。
Phase 4.5: 「これは実装の問題ではなく、設計の問題。」→ アーキテクチャ変更の提案。

### 9.3 デバイス依存バグ診断フロー
iOS Safari / Android WebView 等、実機・シミュレーターでしか再現できないバグ。

**ADVの制約:**
- 静的コード解析のみ可能。シミュレーターでの確認手段を持たない
- **「確定仕様」「唯一の解決策」等の断定表現を使わない**
- 参考情報の提示にとどめる

**正しいフロー:**
1. ENG: 再現スクリプト+スクショ+コンソールログ+ネットワークログをPOに提供
2. PO: 実機で症状を確認
3. ENG: 修正方針をsession_progress.mdに記載→30分待機（ADVがオンラインなら確認）
4. ENG: 実装後シミュレーターで検証→報告
5. ENG→PO: 実機確認依頼→確認後に完了

**ENGの再現報告テンプレート:**
```
症状: （スクショ添付）
再現手順: （1. 2. 3. ...）
コンソールログ: （エラー全文）
ネットワークログ: （失敗リクエスト）
仮説: （最大3つ）
```

### 9.4 補助テクニック
- **Root Cause Tracing:** エラー箇所→呼び出し元を逆方向に辿る
- **Defense in Depth:** 修正後、同種バグが他箇所で起きないよう多層防御
- **Condition-Based Waiting:** `waitForTimeout(3000)`禁止。`waitForSelector`/`waitForResponse`使用

## 13. AIレビュー基盤

### 13.1 レビュー対象
| 対象 | トリガー | 目的 |
|------|---------|------|
| 仕様書 | DRAFT完成時 | 矛盾・漏れ・実現可能性 |
| 設計判断 | アーキテクチャ変更時 | 代替案・リスク分析 |
| コード品質 | 大規模リファクタ時 | 構造・保守性・セキュリティ |
| テスト戦略 | テスト基盤変更時 | カバレッジ・抜け穴 |

### 13.2 実行方式
ENGがAPI経由で複数モデルに**全内容を省略なしで**送信。結果はJSON。
**コスト制御:** 1セッションあたりAIレビュー最大10呼び出し。超過時はPO承認待ち。

### 13.3 結果フォーマット（JSON統一）
```json
[{"id":"R-NNN","severity":"CRITICAL|HIGH|MEDIUM|LOW","category":"CONTRADICTION|COMPLETENESS|FEASIBILITY|AMBIGUITY|BEST_PRACTICE|STRUCTURE","location":"セクション名","issue":"問題","suggestion":"改善提案"}]
```

### 13.4 標準5ペルソナ（カスタム追加可能）
| ペルソナ | 観点 |
|---------|------|
| AI Ops設計者 | AI⇔人間の責務分離。自律範囲と承認ゲート。暴走防止 |
| ソフトウェアアーキテクト | モジュール分離、依存方向、スケーラビリティ |
| QAエンジニア | テストピラミッド、品質ゲートの抜け穴、自動化カバレッジ |
| DevOpsエンジニア | CI/CD、デプロイパイプライン、スクリプト堅牢性 |
| DXエンジニア | ENGが迷わず動ける仕様の明瞭さ。曖昧さ・矛盾 |

### 13.5 統合プロセス
1. ENG: レビュー実行→JSON出力をdocs/plans/に保存
2. ADV: 結果統合→改善計画→PO承認
3. ADV: 改訂版作成
4. 必要に応じて再レビュー→収束
5. 確定版をリポジトリに反映

### 13.6 品質ゲート
- CRITICAL 1件以上 → 改訂必須（確定不可）
- 対応しない指摘には理由を記録
- **review_gate.sh** でdocs/plans/review_*.jsonをスキャンしCRITICAL>0ならFAIL（sub_infrastructure.md参照）

### 13.7 収束ルール
- **最低10ラウンド繰り返す。** 品質改善につながる妥当な指摘がなくなるまで終了しない
- 仕様書に書くべき内容がCRITICALとして指摘された場合、実装時対応ではなく仕様書を修正する
- AIレビューは**推論ではなく事実ベース**で実施する。「〜かもしれない」「〜のリスクがある」ではなく、具体的な矛盾箇所・未定義箇所・動作不能コードを指摘させる
- リーズナブルでない指摘（過度な理想論/現実的でない要求）は棄却理由を記録してスキップ可

### 13.8 レビュー対象の範囲
仕様書だけでなく、以下も同じ基準でAIレビューを実施する：
| 対象 | レビュー観点 |
|------|------------|
| 仕様書 | 矛盾・漏れ・実現可能性・構成の妥当性 |
| 設計方針 | 妥当性・不備・代替案の検討漏れ |
| テスト内容 | 妥当性・不備・カバレッジの抜け |
| 開発体制 | 責務分離・承認フロー・暴走防止の実効性 |

### 13.9 severity inflation対策
修正→再レビューを繰り返すと、構造的問題が解消された後にAIレビュアーがエッジケースのseverityを上げる傾向がある（severity inflation）。以下で対処する：
- 前ラウンドで解消済みのテーマが再出現した場合、レビュアーの指摘が具体的な新事実に基づいているか確認
- 全件CRITICALのような極端な結果は、品質問題ではなくレビュープロセスの限界として棄却可
- 棄却時はADVまたはPOがsession_progress.mdに理由を記録し、該当JSONアイテムに `"dismissed": true, "dismiss_reason": "..."` を追加（review_gate.shが棄却済みCRITICALを除外するため）。ENGが単独でdismissedフラグを設定することは禁止（ADV/PO承認必須）

### 13.10 棄却検証ステップ
レビュアーの指摘を棄却する際のルール:
- ENGがgrep結果のみで「仕様書に存在しない」と判断してはならない。長文行が`[Omitted]`される場合は必ずReadで原文を確認
- **同じ指摘が3ラウンド以上連続で出現した場合:** ENGは棄却を一時停止し、該当セクション全体をReadで再確認→それでも棄却が妥当ならADV/POに棄却理由を報告して承認を得る
- 棄却の根拠は「grep結果が0件」ではなく「Readで該当セクション全体を確認した結果、記述なし」でなければならない

### 13.11 既知矛盾除外リスト
上流仕様書に既知の矛盾が存在し、別途修正予定の場合:
- レビューコンテキスト（AIへのシステムプロンプト）に「既知矛盾リスト」を追加し、レビュアーにこれらをCRITICALとして報告しないよう指示する
- 形式: `以下はproject_v1.mdの既知矛盾であり、本レビューの対象外: [リスト]。これらをCRITICALとして報告しないこと。`
- これにより新規CRITICALの発見効率が向上し、既知矛盾によるレビューノイズを排除する

### 13.12 レビュー効率化（収束後）
CRITICAL数が収束傾向を示した段階（3ラウンド連続でCRITICAL数が減少 or 横ばい）での効率化:
- **ペルソナ絞り込み:** 前ラウンドでCRITICALを出したペルソナのみ再実行。0件のペルソナはスキップ
- **モデル絞り込み:** 新規の有用な指摘の比率が高いモデルのみに絞る。判断基準: 過去3ラウンドで新規CRITICAL/HIGH検出数が多いモデル
- 絞り込み適用時はsession_progress.mdに「R{N}以降: ペルソナ/モデル絞り込み適用。理由: [根拠]」と記録

### 13.13 レビューモデル更新ルール
レビュー開始時に使用するAIモデルの選定:
- レビュー開始時にOpenAI/Google/AnthropicのAPIドキュメントで最新モデルを確認し、利用可能な最高性能モデルを使用する
- ミッション定義にモデル名を記載する際は、その時点の最新モデルを指定。過去のミッション定義からモデル名をコピーしない
- モデル廃止/更新があった場合、進行中のレビューは次ラウンドから新モデルに切替（途中ラウンドは混在可）
- **プロバイダー分離:** ENG（Code）と同一プロバイダーのモデルをレビューモデルに使用しない。クロスチェックの目的は異なるAI思想による盲点検出であり、同一プロバイダーでは盲点が共通する。ENGがClaude系の場合、レビューにClaude APIは不可
- **quota枯渇時のフォールバック:** レビューモデルのquotaが枯渇した場合、ENG（Code）自身が仕様書を直接読んでレビューJSON出力を行う（API経由ではなくCode自身の知性による直接レビュー）。quota復旧後は通常の2モデル体制に戻す

### 13.14 確定済み仕様書の矛盾検出フロー
下流仕様書のレビュー中に上流仕様書（確定済み）の矛盾が発見された場合:
1. ENGはレビュー結果に `"upstream_issue": true` フラグを追加
2. 下流レビューを一時停止（PAUSED）
3. ADVが上流仕様書の矛盾を修正 → バージョン更新 → 変更履歴記録
4. 下流レビューを再開（上流修正を反映した状態で）
- 上流修正なしに下流レビューを収束させることは禁止（矛盾が下流に伝播するため）

### 13.15 レビューコスト最適化

レビューの品質・スピードを維持しつつコストを最小化する。3つの手法を組み合わせる。

#### 13.15.1 3モデル体制

| モデル | コスト | 実行ルール |
|-------|------|----------|
| Claude Code（自身） | ¥0（月額内） | **毎ラウンド全ペルソナ実行。** 追加コストなし。常にフル実行 |
| GPT-5.4 | 従量（API） | R1: 全ペルソナ。R2以降: §13.12に従いCRITICAL出したペルソナのみ |
| Gemini 3.1 Pro Preview | 従量（API） | 同上 |

Claude Codeが常に全ペルソナを回すことで、外部APIの絞り込みを攻められる。Codeが見つけた問題を外部で再検証、Codeが見逃した盲点を外部がカバーする構造。

#### 13.15.2 プロンプトキャッシュ（外部API）

同一ラウンド内で仕様書全文を複数ペルソナに送る際、キャッシュで入力コストを削減。スピードも向上（キャッシュヒットでAPI側処理が高速化）。品質影響なし。

**プロンプト構成順序（必須）:**
```
[1. 仕様書全文（固定。キャッシュ対象）]
[2. 共通プリアンブル（固定。キャッシュ対象）]
[3. ペルソナ指示（可変。ペルソナごとに変わる部分）]
```

**OpenAI（GPT-5.4）:**
- 自動キャッシュ。同じプレフィックス1,024tokens以上で自動適用
- 入力トークン50%OFF。レイテンシも改善
- プロンプト構成順序を守るだけで適用される

**Gemini（3.1 Pro Preview）:**
- Context Caching API を明示的に使用
- 仕様書全文+共通プリアンブルをcachedContentとして作成（TTL: 1時間）
- 各ペルソナレビューはキャッシュ参照+ペルソナ指示のみ送信
- 入力トークン75%OFF
- ラウンド完了後にキャッシュ削除（不要なストレージコスト防止）

#### 13.15.3 差分レビュー（R2以降）

R1は全文送信で構造全体を検証。R2以降は修正箇所+周辺コンテキストのみ送信しトークン量を削減。スピードも向上。

**ルール:**
- R1: 全文送信（70K tokens想定）
- R2-R4: 差分+前後200行のコンテキスト（5-15K tokens想定）
- R5: 全文送信（構造問題の再チェック。以降5R毎に繰り返し）
- Claude Code（コスト¥0）は差分ではなく常に全文で実行可

**差分の定義:** 前ラウンドからのgit diffで変更されたセクション（§単位）+その前後の§を含む

#### 13.15.4 ラウンド別実行フロー

```
Pre-Review（外部API投入前。コスト¥0）:
  Claude Code: 全ペルソナ × 全文 → CRITICAL/HIGH抽出
  Claude Code: 自律修正 → 再レビュー → CRITICAL 0になるまで繰り返し
  ※ Codeの月額内で完結。何ラウンド回してもコスト¥0
  ※ Pre-Review完了条件: Code自身のレビューでCRITICAL 0

R1（外部API初回。Pre-Review済みの高品質な仕様書で開始）:
  Claude Code: 全ペルソナ × 全文 → ¥0
  GPT-5.4:     全ペルソナ × 全文（キャッシュ適用）
  Gemini:      全ペルソナ × 全文（キャッシュ適用）

R2-R4（修正検証）:
  Claude Code: 全ペルソナ × 全文 → ¥0
  GPT-5.4:     CRITICAL出したペルソナのみ × 差分（キャッシュ適用）
  Gemini:      CRITICAL出したペルソナのみ × 差分（キャッシュ適用）

R5（全文再チェック）:
  R1と同じ構成

R6以降:
  R2-R4と同じ構成。5の倍数ラウンドでR5と同じ
```

**Pre-Reviewの効果:**
- Codeが見つけられる問題（矛盾/未定義/構造不備）を事前に全て修正
- 外部APIは「Codeでは見つけられなかった盲点」の発見に集中
- 外部APIのR1時点で既にCRITICALが少ない → 収束までのラウンド数が大幅減少（14ラウンド→推定7-8ラウンド）

#### 13.15.5 コスト試算（70K tokens入力。Pre-Review導入後）

| 手法 | 外部APIラウンド数 | コスト | 削減率 | スピード |
|------|----------------|-------|--------|---------|
| 最適化なし（現状） | 14 | ~$71 | — | 基準 |
| キャッシュのみ | 14 | ~$27 | 62% | ⬆️向上 |
| キャッシュ+差分+絞り込み | 14 | ~$10 | 86% | ⬆️大幅向上 |
| **Pre-Review+キャッシュ+差分+絞り込み** | **7-8** | **~$5** | **93%** | **⬆️大幅向上** |

Pre-Review（Code自身の修正サイクル）は何ラウンド回しても¥0。上記コストに含まない。

**ai_review.js実装要件:**
1. 仕様書全文+共通プリアンブルを1つの文字列として結合
2. ペルソナ指示を分離
3. OpenAI: プレフィックスとして結合文字列→ペルソナ指示の順で送信
4. Gemini: cachedContent API で結合文字列をキャッシュ→各ペルソナはキャッシュ参照+ペルソナ指示
5. R2以降: git diff → 変更§を特定 → 差分+前後§を抽出 → 差分プロンプト構築
6. Claude Code実行: 外部APIと並列で自身がレビューJSONを生成（APIコールなし。自身の推論で実行）
7. ラウンド完了後にGeminiキャッシュを削除
8. レビューJSON命名規則（Pre-ReviewとAPIレビューの混入防止）:
   - Pre-Review: `review_{mission}_pre_r{N}_{persona}.json`
   - 外部API: `review_{mission}_r{N}_{model}_{persona}.json`
   - cmd2のCRITICALカウントは最終ラウンドのファイルのみ対象。stale feedbackの混入を防ぐ

**適用タイミング:** 即時（次回レビューから適用）。

#### 13.15.6 レビューモデル使い分け（PO承認済み 2026-04-15）

品質ゲートの最終判定にはトップモデルを使い、中間確認は品質維持できる範囲でコストを下げる。

| フロー段階 | モデル | 理由 |
|-----------|--------|------|
| ゴールデンレビュー（R1 / 最終確認） | GPT-5.4 | 品質の最終ゲート。ここで見逃したら本番に出る |
| 修正ラウンド（R2〜R4の差分レビュー） | GPT-5 | 「直した箇所が壊れてないか」の確認。差分のみで入力少ない |

モデルIDは開始時にAPI最新モデルを確認すること（コピー禁止）。

### 13.16 レビュー学習パターン蓄積（Learned Patterns）

レビューで繰り返し指摘されるパターンを蓄積し、次の実装で事前に適用することで同じ指摘の再出現を防止する仕組み。

#### 13.16.1 目的
- 同一または類似する指摘が複数ミッションで繰り返されるコストを排除する
- ENGが新コンポーネント実装時に過去の学習を自律的に適用する

#### 13.16.2 対象
- severity を問わない（CRITICAL/HIGH/MEDIUM/LOW 全て対象）
- 2つ以上の異なるミッションで同一または類似の指摘が出現したパターンのみ蓄積する
- 1ミッション内で複数レビュアーが指摘しても、他ミッションで再出現しなければ蓄積しない
- **予防適用の成功も再出現にカウントする。** ミッションAで指摘→修正し、ミッションBで事前適用して指摘を防いだ場合、「2ミッションで出現」として蓄積対象とする（LP蓄積フローが正しく機能した証拠であり、昇格しない理由にはならない）

#### 13.16.3 蓄積ファイル
- パス: `docs/learned-patterns.md`（ENGが管理。ADVは仕組みのみ定義）
- テンプレート: `templates/learned_patterns_template.md`

#### 13.16.4 蓄積フロー
```
ゴールデンレビュー CRITICAL 0 達成
  → ENGが全指摘（severity不問）を docs/learned-patterns.md の既存パターンと照合
  → 過去ミッションの指摘と同一・類似するものを特定
  → 2ミッション以上で出現したパターンのみ追記（初出ミッション名を記録）
  → 1ミッションのみの指摘は追記しない
```

#### 13.16.5 適用フロー
```
新コンポーネント実装開始前
  → ENGが docs/learned-patterns.md を読む
  → 該当するパターンを実装時に事前適用
  → レビューパッケージに「適用済みパターン一覧」を記載
```

#### 13.16.6 パターンのエントリ形式
```markdown
### LP-NNN: パターン名
- **何をすべきか:** 具体的な実装指針（1-2行）
- **やらないとどうなるか:** レビューで指摘される内容
- **初出:** M2（S-00 Splash）
- **再出現:** M3（S-01 Auth）, M4-A（AuthCallback）
```

#### 13.16.7 過度適用の防止
- パターンは「該当する場面でのみ」適用する。全コンポーネントに機械的に適用しない
- パターンの適用判断はENGに委ねる。判断に迷う場合は適用しない側に倒す
- 蓄積数が50件を超えた場合、直近10ミッションで一度も該当しなかったパターンをアーカイブする

### 13.17 ENG自律判定（3ペルソナ制）

ENGがミッション間の判断（レビュー結果対応方針・LP昇格・次ミッション定義・スコープ判定等）をPO介在なしで自律実行するための仕組み。

#### 13.17.1 目的
- PO（ふとし）の中継作業を排除し、Codeが自律的にミッション間判断を行う
- 判断品質を担保するため、ENG単独ではなく3ペルソナの合議で判定する

#### 13.17.2 ペルソナ定義

**① ADV（アドバイザー）**
- 役割: 仕様・技術・品質の判断者
- 入力: dev-system仕様 + アプリ仕様書 + 判断テーブル + learned-patterns.md
- 責務: レビュー結果の分類・対応方針 / 技術方針の確定 / ミッション定義の自動生成 / LP昇格判定 / 仕様変更の検知

**② QA（品質管理）**
- 役割: ADVの判断が「ルール通りか」を検証する審判
- 入力: dev-system全文 + CLAUDE.md + development_rules.md
- 責務: ルール適用の正確性検証 / 判断テーブル該当性チェック / 仕様書間整合性 / 書き込み前の連鎖更新確認 / 品質ゲート迂回の検出

**③ PO代理（ふとし代理）**
- 役割: 「ふとしならどう判断するか」をPO判断パターン集に基づいて検証する
- 入力: docs/po-decisions.md + session_historyのPO判断記録
- 責務: ADV判断の妥当性検証 / エスカレーション判定 / 優先順位検証 / scope creep・過剰品質の抑止

#### 13.17.3 判定フロー
```
判断が必要な場面が発生
  Step 1: ADVが判断を出す（1-2行）
  Step 2: QAが検証（1行。ルール適用は正確か）
  Step 3: PO代理が検証（1行。PO方針と整合するか）
  → 3者合意 → 実行。記録は「ADV判定: / QA検証: / PO代理: 」の3行
  → 不合意 → POエスカレーション（3者の意見を添えて報告）
```

#### 13.17.4 判断テーブル（ADVが即判定できる定型パターン）

| 場面 | 判定 |
|------|------|
| ゴールデンCRITICAL 0達成 → HIGH対応 | Phase A完了後まとめて。security HIGHのみ提案ログ記録 |
| スコープ外CRITICAL | A-a方式: スコープ明示して再レビュー |
| session_progress完了記録 | 書いてOK（ADV記載済み部分との差分確認必須） |
| LP蓄積判定 | §13.16.2ルール適用 |
| 次ミッション定義が未定義 | design_spec §4.X から自動生成（v2テンプレート準拠） |
| レビューモデル選定 | ゴールデン=GPT-5.4 / 修正ラウンド=GPT-5 |

#### 13.17.5 POエスカレーション必須条件
- コスト構造・プラン間差別化に影響する変更
- 新規プロセス・ルールの導入
- ブランド・UXコンセプトの変更
- PO代理が「PO判断パターンに類似ケースがない」と判定

#### 13.17.6 PO判断パターン集
- パス: `docs/po-decisions.md`（ENGが管理）
- POが判断を下した都度、ENGが本ファイルに追記する
- PO代理ペルソナはこのファイルを読んで判断の妥当性を検証する

### 15.6 技術負債管理

**技術負債の定義:**
「今は動作するが、放置すると将来の変更コスト・バグリスクが増大するコード/設計/テスト/ドキュメントの課題」を技術負債とする。
具体例:
- 提案ログに記載されたまま未対応の改善項目
- test.skip()で一時的にスキップされたテスト
- 300行超過のコンポーネント（分割未実施）
- 仕様書に「v0.2.0以降で検討」と先送りされた項目
- ハードコードされた設定値（app_config.yaml未移行）

**負債比率の計測:**
```
負債比率 = 提案ログ未処理件数 / 直近10ミッション完了件数 × 100%
```
- 棚卸し（5セッションごと）の際に計測
- session_progress.mdの提案ログと完了済みミッションから算出

**閾値と対応:**
| 負債比率 | 状態 | 対応 |
|---------|------|------|
| 0-20% | 健全 | 通常運用 |
| 21-30% | 注意 | 次のミッション選定時に負債返済を1件以上含める |
| 31%以上 | 危険 | 新機能ミッションを停止し、負債返済スプリントを実施。比率が20%以下に戻るまで |

**負債返済スプリント:**
- 提案ログから優先度順に負債を選定（コスト影響あり > テスト品質 > コード品質 > ドキュメント）
- 通常ミッションと同じフロー（ミッション定義v2テンプレート準拠）で実行
- 返済完了後に負債比率を再計測

**適用開始タイミング:** アプリ実装フェーズ（Phase 4）開始時。仕様書フェーズでは提案ログの蓄積のみ。

## 16. 構造的制約

同一バグ修正は3回まで。3回失敗→HOLD→ADVエスカレーション。§9.2参照。

### 16.2 300行制限
session_progress.mdは300行以内維持。超過時はsession_archiver.sh（sub_infrastructure.md）でアーカイブ。

### 16.3 ホットフィックスパス
ux_v*.md記載の機能を変更しない + 対象2ファイル以内 → ENG自律実行可（🟢低リスク）
**上限:** 1セッション2件 / 変更ファイル合計≤4。連続2セッションまで。

### 16.4 ENGのエラー報告
「忘れた」「間違えた」禁止。構造的根本原因と再発防止策をテンプレートで報告：
```
問題: （何が起きたか）
構造的原因: （仕組みの問題として記述）
再発防止策: （どのルール/ゲート/チェックを追加するか）
反映先: （どのファイルに書き込むか）
```

### 16.5 絶対禁止（正本。sub_adv_protocol.mdからは参照のみ）
- canopy項目削除（追加は可、削除はPO承認必須）
- 契約変更（CLAUDE.md無断変更）
- UI変更をgrep確認だけで「完了」にすること
- ログ確認前の投機的修正
- 分母なしの「ALL PASS」「全件完了」報告
- 対象ファイル外の変更（changed-files-allowlist.shでFAIL）
- TDD証跡なしの完了報告（evidence/にbefore/after必須）

### 16.6 改善提案ルール（毎セッション実行）
6視点から優先度付きで最低3つ提案：
🤝営業 / 🔧エンジニア / 📋PM / 🏗️アーキテクト / 💻SE / 👤エンドユーザー
競合差別化提案を1〜3つ別枠で提示。

### 16.7 変更時の一括更新義務
仕様・方針・ルールの変更発生時、PO承認を得た上で関連する全ファイルを一括更新する。

### 19.7 競合ベンチマーク要件

各仕様書の作成前に、その仕様書のスコープに対応する競合ベンチマークを実施する。

**実施タイミング:**

| 仕様書 | ベンチマーク対象 | 調査項目 |
|--------|---------------|---------|
| project_v1.md | ビジネスモデル/機能 | 直接競合5社+間接競合3社。機能マトリクス/価格比較/App Storeレビュー分析（★1-2離脱要因、★4-5継続要因） |
| ux_v1.md | UXパターン | 競合5社の画面構成/遷移パターン/オンボーディング/空状態/エラー表示/ジェスチャー/アニメーション |
| design_system.md | ビジュアルデザイン | 競合5社のデザイン言語/カラースキーム/タイポグラフィ/テーマ切替/アイコン体系 |

**ベンチマーク実施方法（ADVの能力制約に関する注記）:**
ADV（Claude.ai）は実機操作・アプリダウンロード・最新App Storeレビューへの直接アクセスが制限される場合がある。ベンチマーク調査は以下の方法で行う:
1. **POが提供する情報:** POがApp Storeレビュー・競合アプリのスクリーンショット・公式サイト情報を収集してADVに共有
2. **Web検索ツール:** ADVがWebSearch/WebFetchツールを使用して公開レビュー・比較記事・機能ページを調査
3. **事実確認:** ADVはベンチマーク表の各項目に調査日と情報源を明記。未確認項目は「未確認」と明記し、推測で記入しない（鉄則⑧準拠）
4. **ハルシネーション防止:** 情報源のない競合データ（機能有無・価格・レビュー引用）は記載禁止

**ベンチマーク出力フォーマット:**

```markdown
### 競合ベンチマーク: {対象領域}

#### 調査対象
| # | アプリ名 | カテゴリ | DL数/評価 | 調査日 |
|---|---------|---------|----------|-------|

#### 機能/UX/デザインマトリクス
| 機能/パターン | 競合A | 競合B | 競合C | 競合D | 競合E | Lais方針 |
|-------------|-------|-------|-------|-------|-------|---------|

#### 差別化マッピング
| # | 競合の課題（レビューから） | Laisの対応方針 | 対応セクション |
|---|------------------------|-------------|-------------|
```

**差別化マッピングの必須ルール:**
- 全ベンチマーク項目に「Lais方針」列を必ず設ける
- 「同等」「未対応」「差別化」の3分類
- 差別化項目はproject_v1.md/ux_v1.mdの該当セクションと紐付け

**ベンチマーク完了基準:**
- 直接競合5社以上の調査完了
- 機能マトリクスの全行に「Lais方針」が記入済み
- 差別化ポイントが3つ以上明示

**Phase 0の完了基準:** project_v1.mdがベンチマーク実施済み + AIレビューでCRITICAL 0を達成。ペルソナ数はアプリ仕様書の§10（レビュー計画）で定義（project_v1.mdが自身のレビューペルソナを決める。dev-system §13.4の5ペルソナはdev-system自身のレビュー用）。

### 19.9 デザイン実装忠実度（AI開発向け）

AI（Claude Code/Cursor等）によるUI実装で、モックアップとの乖離を防止するための必須プロセス。
Web調査（2026-04-12実施）に基づく、実証済みの5アプローチを統合。

**問題の実態:** AIはコードトークン（クラス名・スタイルプロパティ）で推論するが、ビジュアルで判断しない。色のズレ・余白の差異・要素の順序入替・SVG簡略化は構文チェックでは検出できない。実測値では初回生成の忠実度は65〜80%程度。

**必須プロセス（優先度順）:**

**A. 構造化デザイントークン（design_system.md + CLAUDE.md）**
- design_system.mdに全CSSトークンを16進値で明記（カラー/スペーシング/タイポグラフィ/ボーダー/シャドウ）
- CLAUDE.mdのDesign Contextセクションにdesign_system.md参照を必須化
- Tailwind/CSS変数のconfigとdesign_system.mdの二重制約を設ける
- AIへのプロンプトでは「padding: 16px」ではなく「var(--spacing-md)」のトークン名で指示

**B. ビジュアルリグレッションテスト（VRT）**
- Playwright `toHaveScreenshot()` をE2Eテストに組み込み
- UI変更を含むPRでは、変更前後のスクリーンショット比較を必須化
- 閾値: ピクセル差分0.5%以下でPASS（テーマ切替等の意図的変更は除外リストで管理）
- CI/CDパイプラインに組み込み、VRT FAILでマージブロック

**C. モックアップ原本配信と比較（既存C16強化）**
- モックアップHTMLはlocalhostで配信し、ブラウザでレンダリングした状態で比較（手書き再構成禁止）
- 比較方法: モックアップと実装を横並びでスクリーンショット撮影 → 差分を報告
- 実装にあってモックアップにないUI要素も報告対象

**D. AIの自己検証ループ**
- AI（Code）がUI変更を実装した後、page.screenshot()で結果を撮影
- 撮影したスクリーンショットを画像として見て、仕様通りの視覚変化が起きているか自己判定（鉄則⑨準拠）

| * → BLOCKED | 外部障害・ツール故障等で続行不能 | ENG 手動（「**BLOCKED 理由:**」行必須）|
| DONE / READY_FOR_DEPLOY / IN_PROGRESS → 前状態（4種逆方向） | AI 誤判定の事後訂正 | **ADV / PO のみ**（`canopy_common.sh::correct_status()` 経由、`instructions/status_corrections.log` 記録必須、ENG 独断禁止）— 下記 STATUS_CORRECTION 例外規定参照 |

**BLOCKED 例外規定:**
- ENG は IN_PROGRESS 中に外部依存障害・ツール故障・スクリプトバグ等で続行不能と判断した場合のみ手動遷移可
- session_progress.md 該当ブロックに「**BLOCKED 理由:** <理由>」の行を STATUS 直下に追記（必須）
- BLOCKED 解除も ENG 手動。「**BLOCKED 解除:** <日時> <理由>」を追記
- canopy::check_blocked_integrity が BLOCKED without reason を検出し FAIL
- BLOCKED 以外の STATUS 手動書換えは禁止（鉄則⑭「ルールを曲げるな、変えろ」）

**STATUS_CORRECTION 例外規定（PATCH-12、PD-109 拡張）:**
- ADV/PO は canopy_common.sh::correct_status() 経由で逆方向遷移を実行可
- 許容遷移: DONE→READY_FOR_DEPLOY / DONE→IN_PROGRESS / READY_FOR_DEPLOY→IN_PROGRESS / IN_PROGRESS→QUEUED（4種）
- 全履歴を instructions/status_corrections.log に記録。本ログは ADV書込可、ENG書込不可（changed-files-allowlist.sh で制約）
- ENG の独断逆方向書換えは禁止（correct_status の caller_role=ENG は関数内 exit 1）
- BLOCKED への correct_status は禁止（BLOCKED は正規例外遷移であり誤判定対象外）
